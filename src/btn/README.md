# Button

Модуль обработки кнопки состоит из двух связанных уровней:

- [btn_hw.md](btn_hw.md) — аппаратный уровень;
- [btn.md](btn.md) — логический уровень.

Вместе они образуют единую последовательность:

~~~ text
GPIO
 │
 ▼
btn_hw
 │
 ├── GPIOTE
 ├── debounce
 └── confirmed physical state
          │
          ▼
         btn
          │
          ├── PRESS
          ├── RELEASE
          ├── SINGLE_PRESS
          └── DOUBLE_PRESS
          │
          ▼
      event queue
~~~

## btn_hw

[btn_hw.md](btn_hw.md) описывает нижний аппаратный слой.

Он отвечает за:

- обнаружение изменений GPIO через GPIOTE;
- устранение дребезга;
- первоначальный debounce после запуска;
- подтверждение стабильного физического состояния;
- передачу подтверждённого состояния в btn.

Главный вопрос этого уровня:

> Какое физическое состояние кнопки сейчас действительно подтверждено?

## btn

[btn.md](btn.md) описывает верхний логический слой.

Он получает от btn_hw только подтверждённые значения pressed и
преобразует их в события:

- PRESS;
- RELEASE;
- SINGLE_PRESS;
- DOUBLE_PRESS.

Он также отвечает за:

- завершение циклов PRESS → RELEASE;
- double-press interval;
- double-press timer;
- очередь событий;
- выдачу событий через btn_event_take().

Главный вопрос этого уровня:

> Что означает подтверждённое физическое состояние кнопки с точки зрения приложения?

## Граница между уровнями

Граница проходит по callback:

~~~ c
btn_hw_callback_t
~~~

который передаёт в btn только:

~~~ c
bool pressed
~~~

Поэтому btn_hw не знает о пользовательских событиях, а btn не знает
о GPIO и debounce.

## Рекомендуемый порядок чтения

1. [btn_hw.md](btn_hw.md) — сначала разобраться, как физическое состояние
   обнаруживается и подтверждается.
2. [btn.md](btn.md) — затем посмотреть, как подтверждённое состояние
   преобразуется в события приложения.

Так два файла читаются как описание одного сквозного механизма, а не как
две независимые документации.
