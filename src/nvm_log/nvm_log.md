# nvm_log — одностраничный журнал во flash

## Назначение

`nvm_log` предоставляет простой журнал последовательных 32-битных значений в одной странице внутренней flash nRF52840. Модуль хранит записи и позволяет прочитать последнюю сохранённую запись.

Это не универсальный слой работы с памятью: размер записи фиксирован и равен одному слову (32 бита). Модуль не знает структуру payload и не интерпретирует его содержимое.

## Публичный интерфейс

```c
bool nvm_log_init(uint32_t free_value_mask);
bool nvm_log_save(uint32_t data);
bool nvm_log_load(uint32_t *data);
```

- `nvm_log_init()` задаёт маску свободной ячейки и сканирует существующий журнал. Успешная инициализация допускается один раз.
- `nvm_log_save()` добавляет одно 32-битное значение в следующую свободную ячейку.
- `nvm_log_load()` возвращает последнее сохранённое значение.

Все функции возвращают `false` при нарушении предусловий или ошибке операции. `nvm_log_load()` также возвращает `false`, если записей нет или указатель результата равен `NULL`.

## Flash region

Модуль использует первую страницу Application Data Area:

| Параметр | Значение |
|---|---:|
| Начальный адрес | `0xDD000` |
| Размер страницы | 4096 байт |
| Размер записи | 4 байта |
| Количество ячеек | 1024 |
| Адресное пространство | Внутренняя flash nRF52840 |

В конфигурации используемого bootloader Application Data Area занимает три страницы, начиная с `0xDD000`. `nvm_log` использует только первую из них. Размещение зависит от linker/bootloader configuration и не является автоматически обнаруживаемым модулем.

## Формат и распознавание свободной ячейки

После erase все биты flash-слова установлены в 1, поэтому значение пустой ячейки — `0xFFFFFFFF`. Однако caller задаёт не одно фиксированное значение, а `free_value_mask`.

Ячейка считается свободной, если:

```c
(value & free_value_mask) == free_value_mask
```

Caller обязан выбрать маску так, чтобы ни одно допустимое значение payload не удовлетворяло этому условию. Значения, которые совпадают с шаблоном свободной ячейки, зарезервированы и не могут быть записаны.

Такой контракт позволяет использовать payload-specific свободный шаблон, не заставляя `nvm_log` знать формат записи. Модуль не проверяет корректность самой маски и не может определить, действительно ли она исключает все допустимые payload.

## Организация журнала

Записи размещаются последовательно от начала страницы. При инициализации модуль читает ячейки по порядку и останавливается на первой свободной. Все предыдущие ячейки считаются занятыми, а последняя из них — последней сохранённой записью.

`m_used_cell_count` хранит количество занятых ячеек и одновременно индекс следующей ячейки для записи. `m_latest_index` указывает на последнюю сохранённую запись; `m_has_latest` отдельно показывает, существует ли такая запись.

Предполагается, что журнал непрерывен: после первой свободной ячейки записей нет. Модуль не ищет записи после пропуска и не восстанавливает журнал после произвольного повреждения последовательности.

## Сохранение

`nvm_log_save(data)`:

1. Проверяет, что модуль инициализирован и значение не совпадает с шаблоном свободной ячейки.
2. Если все 1024 ячейки заняты, стирает всю страницу.
3. Вычисляет адрес следующей ячейки по индексу `m_used_cell_count`.
4. Проверяет возможность программирования слова через `nrfx_nvmc_word_writable_check()`.
5. Записывает слово через `nrfx_nvmc_word_write()` и ждёт завершения через `nrfx_nvmc_write_done_check()`.
6. Только после завершения записи обновляет состояние журнала в RAM.

Если страница заполнена, старые записи стираются перед записью нового значения. Это кольцевое поведение на уровне одной страницы, но не полноценный wear-leveling: используется одна физическая страница и при каждом заполнении выполняется её erase.

Сбой питания во время erase может привести к потере всех записей страницы, включая последнее сохранённое значение. Модуль не реализует транзакционный commit marker, резервную копию или восстановление после прерывания erase.

## Загрузка

`nvm_log_load(data)` проверяет инициализацию, указатель и наличие хотя бы одной записи. Затем напрямую читает последнее сохранённое 32-битное слово из memory-mapped flash и возвращает его через `data`.

Чтение не требует отдельной NVMC функции. Адрес вычисляется из базового адреса страницы и индекса ячейки.

## NVMC API

Для операций записи и стирания модуль использует:

- `nrfx_nvmc_page_erase()` — стирание всей страницы;
- `nrfx_nvmc_word_writable_check()` — проверка возможности программирования слова;
- `nrfx_nvmc_word_write()` — запись 32-битного слова;
- `nrfx_nvmc_write_done_check()` — ожидание завершения записи.

Чтение выполняется обычным чтением из memory-mapped flash. Модуль не использует API для произвольных размеров, выравнивания или адресных диапазонов.

## Использование в HSV Picker

Вызывающий слой формирует payload и маску, поскольку только он знает допустимые данные. В HSV Picker компоненты упакованы так:

| Биты | Компонент |
|---|---|
| 0…15 | Hue |
| 16…23 | Saturation |
| 24…31 | Value |

Маска `HSV_FREE_VALUE_MASK` выбирается так, чтобы шаблон свободной ячейки не совпадал ни с одной допустимой комбинацией HSV. После чтения `hsv_picker` самостоятельно распаковывает слово и проверяет H = 0…359, S/V = 0…100.

Таким образом, `nvm_log` отвечает только за последовательное хранение 32-битных значений, а прикладной слой — за смысл и валидацию данных.

## Ограничения

- Используется одна фиксированная flash page; размер и адрес заданы внутри модуля.
- Записи имеют фиксированный размер 32 бита.
- Caller обязан предоставить корректную `free_value_mask`.
- Записи должны занимать непрерывный префикс страницы.
- При заполнении стирается вся страница и теряется история предыдущих записей.
- Нет wear-leveling, commit marker, резервирования или защиты от потери питания во время erase.
- Инициализация поддерживает один экземпляр модуля и выполняется один раз.
- Данные других форматов в выбранной странице не распознаются и не защищаются от перезаписи.
